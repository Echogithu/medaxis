# 患者端与管理员后台界面审查

日期：2026-10-08。结论：优先修正操作反馈、入口一致性和列表完整性，然后优化手机上的任务层次。两端已有统一的导航、卡片和主色，不需要先做全站视觉重做。

本轮只审查，未修改产品源码、接口、权限或数据库。依据当前源码、20 个页面在 1440px/390px 下的合成数据渲染、定向问题复现；不代表真实后端、外部模型、邮件发送、医生接诊或医疗内容验收通过。所有 API 请求均由本地夹具接管，写请求阻止；邮箱和身份均为合成数据。

## 需要先明确的产品决定

这些是建议和待确认事项，不是本轮已修改的功能。

1. **语音是否属于当前版本？** 01可以通过明确未开放消除误导；实现语音识别需要另定功能范围。
2. **注册时省份为什么必填？** `RegisterPage.tsx:72` 强制省份；手机表单还集中收集年龄、月龄、性别、地址等资料，提交按钮在很下方。若无注册时的业务必要性，建议后续补充；不能未经确认移除必填约束。登录手机首屏也可缩短介绍，把登录操作提前。
3. **复查任务完成是否必须填反馈？** `FollowUpPage.tsx:213-218`：复选框可直接完成，旁边按钮可填反馈。两者不同不必然是错误。若允许快捷完成，文案应区分“标记已完成”和“填写复查情况”；若要求反馈，再统一完成流程。
4. **注册后进入问诊、登录后进入今日健康是否刻意？** `RegisterPage.tsx:188`、`LoginPage.tsx:112-118`；可以保留新用户引导，但要清楚表达下一步，不为一致性强行统一。
5. **账号找回渠道是什么？** 本轮在登录页和已注册的公开路由中没有找到找回入口；不能由此推断仓库外不存在支持渠道。先明确渠道，再决定入口。

## 没有列为缺陷的两项

- `AdminLayout.tsx:157-195` 调用身份接口并检查管理员角色，不能仅凭 App 的路由写法断言没有管理员守卫。这也不等于后端权限已经做完专项验收。
- 审核队列把类型显示成“病例报告”符合当前后端只查 `DocType.CASE_REPORT` 的约束（`backend/app/api/v1/admin.py:1056-1058`）；暂不要求根据其他类型映射。
- 用户要求的是总结先显示可能的问题，且“请先注意这些情况”在“还要注意什么”之前。没有要求它紧邻主要判断；本轮不以此误报缺陷，也不调整已接受顺序。

## 推荐实施与验收顺序

1. **操作与状态**：上传超限反馈、聊天重试、站内信重置、中文状态；语音先明确当前可用范围。验收包括失败后重试、空结果、输入保留和无虚假成功。
2. **入口与查找**：报告入口一致，完整用户/医生列表与可靠分页，常用审核/日志筛选。覆盖超过100条、第二页、最后一页、筛选后清空、报告中心未就绪。
3. **手机信息层次**：先完成一条任务，再看统计；后台固定操作或改对象卡；药物分组。覆盖320/390/768/1440px，触摸和键盘可发现性，不只检查横向溢出。

上述为建议，不代表已批准实施。新增语音、放宽注册要求、改变完成规则、分页接口扩展都需明确决定；现有权限、同意与医疗提示不能因“简化界面”而削弱。
